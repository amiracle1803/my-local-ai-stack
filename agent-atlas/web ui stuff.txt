## 14. Redundancy and Resilience Architecture

This section expands the redundancy concept into a concrete resilience strategy for models, runtime, and data.[memory:21]

### 14.1 Model and Provider Resilience

- **Capability matrix**  
  Maintain a matrix mapping each model to capabilities (e.g. `deep_reasoning`, `web_research`, `cheap`, `private`, `fallback`). Model Router uses this matrix plus config flags.

- **Provider health checks**  
  Observability Agent periodically tests:
  - Hermes endpoint.
  - Claude API.
  - Perplexity API.
  - Local fallback endpoints.

  Results stored as `provider_status` with `healthy | degraded | down` and recent latency.

- **Routing with health and privacy**  
  Model Router, when picking a model, must consider:
  - Desired capabilities.
  - Privacy constraints (`LOCAL_ONLY`, task `privacy_level`).
  - Health state; down providers are ignored.
  - Cost budgets and past error rates.

- **Graceful degradation**  
  If Perplexity is down:
  - Knowledge Hub automatically falls back to Obsidian + Retrieval Agent.
  If Claude is down:
  - Orchestrator uses Hermes/local specialists with extra planning steps and smaller context windows.

### 14.2 Job and Runtime Resilience

- **Checkpoint strategy**
  - For multi‑step tasks, define explicit checkpoints, for example:
    - `plan_created`, `evidence_collected`, `draft_v1`, `draft_v2`, `ai_approved`, `human_approved`, `execution_step_n`.
  - Background Runtime updates the job record with the latest checkpoint and necessary context (e.g., which version index is current).

- **Idempotent tool design**
  - Each tool invocation in Action Hub includes an `idempotency_key` based on task id + step id.
  - Tools must:
    - Check for prior execution of the same key.
    - Either return the stored result or no‑op if already executed.

- **Timeouts and retries**
  - Each job has a max execution time per step and total retry attempts.
  - If a step times out:
    - Retries are scheduled using exponential backoff.
    - After max retries, the task goes to `FAILED` or `AWAITING_HUMAN` with error context.

### 14.3 Data and Knowledge Resilience

- **DB and file backups**
  - Periodic export of critical tables:
    - `jobs`, `memory_*`, `agent_traces`, `metrics`.
  - Exports as JSONL or CSV into `data/exports/YYYY-MM-DD/`.

- **Obsidian as long‑term memory**
  - Automation Agent can:
    - Write daily/weekly “Agent Atlas log” notes summarizing important tasks and decisions.
    - Keep a high‑level changelog of major system configuration changes.
  - This allows you to reconstruct decision history even if DB data is lost or migrated.

## 15. Multi‑Pass Review and Confirmation Pipeline

This section formalizes the multi‑angle, multi‑round review process you wanted, with human‑in‑loop gating for high‑risk tasks.[memory:22]

### 15.1 ReviewPolicy Definition

Each task has a `ReviewPolicy` attached at creation:

```ts
type ReviewerRole =
  | "factual"
  | "safety"
  | "code_quality"
  | "style"
  | "cost";

interface ReviewPolicy {
  requiredReviewers: ReviewerRole[];     // which dimensions must review
  minScores: Partial<Record<ReviewerRole, number>>; // e.g. { factual: 0.9, safety: 0.99 }
  minRounds: number;                     // minimum AI review/improvement cycles
  maxRounds: number;                     // to prevent infinite loops
  requiresHumanBeforeExecution: boolean; // for side-effecting tasks
  requiresHumanBeforeCompletion: boolean;// for final acceptance
}
```

Policy presets (configurable):

- `low_risk_quick` – 1 round, factual + style reviewers, no human gate, no side effects.
- `medium_risk` – 2–3 rounds, factual + safety reviewers, human gate optional.
- `high_risk` – 3–5 rounds, all reviewers, human approval mandatory before execution.

### 15.2 Reviewer Agents

Define specialized reviewer agents using the Collaboration Bus:

- **Factual Reviewer**
  - Uses Knowledge Hub + Retrieval Agent.
  - Checks that claims are supported by evidence.
  - Penalizes hallucinations, missing citations, and outdated info.

- **Safety Reviewer (Guardian)**
  - Enforces content and action policies.
  - Blocks tasks that:
    - Leak secrets or sensitive data to remote providers against policy.
    - Attempt high‑risk tools without required approvals.

- **Code Quality Reviewer**
  - Applies to tasks that produce or modify code.
  - Uses Code Agent + tests/lints to evaluate:
    - Correctness, maintainability, adherence to style guide.

- **Style/Structure Reviewer**
  - Applies to docs, responses, UI text.
  - Checks clarity, structure, and optional user‑defined style rules.

- **Cost/Performance Reviewer**
  - Observes token usage, model choice, latency, and number of agents involved.
  - Suggests simpler workflows for similar future tasks.

Reviewer response schema:

```json
{
  "role": "factual",
  "score": 0.94,
  "verdict": "approve",   // "approve" | "revise" | "block"
  "feedback": [
    {
      "severity": "high",
      "message": "Claim about X is not supported by any cited source."
    },
    {
      "severity": "low",
      "message": "Consider simplifying explanation of Y."
    }
  ]
}
```

### 15.3 State Machine & Loops

Task states (simplified):

- `DRAFT` – initial output from one or more agents.
- `AI_REVIEW_IN_PROGRESS` – reviewer agents evaluating output.
- `AI_NEEDS_IMPROVEMENT` – review concluded that revision is required.
- `AI_REVISED` – new version produced.
- `AWAITING_HUMAN` – waiting for human decision.
- `APPROVED_FOR_EXECUTION` – cleared for side effects.
- `EXECUTING` – tools and runtime executing plan.
- `COMPLETED` / `FAILED` / `STOPPED` – terminal states.

Loop logic:

1. Orchestrator gets first candidate output → `DRAFT`.
2. Orchestrator submits candidate to Collaboration Bus → reviewer agents → `AI_REVIEW_IN_PROGRESS`.
3. Once all required reviewers respond:
   - Aggregate scores and verdicts.
   - If any `block` or scores < thresholds:
     - State → `AI_NEEDS_IMPROVEMENT`.
   - Else if rounds < `minRounds`:
     - Treat as `AI_NEEDS_IMPROVEMENT` to force another improvement pass.
   - Else if no human gate required:
     - State → `APPROVED_FOR_EXECUTION` or `COMPLETED`.
   - Else:
     - State → `AWAITING_HUMAN`.

4. In `AI_NEEDS_IMPROVEMENT`:
   - Orchestrator creates a feedback packet from all reviewer feedback.
   - Sends it back via Collaboration Bus to the agent(s) that produced the candidate.
   - They generate a new version → `AI_REVISED` → back to `AI_REVIEW_IN_PROGRESS`.

5. If `maxRounds` exceeded:
   - Task escalates directly to `AWAITING_HUMAN` with explanation:
     - “AI could not satisfy review policy in N rounds. Here are the best and worst attempts.”

6. In `AWAITING_HUMAN`:
   - Human uses Review Center to:
     - Approve → `APPROVED_FOR_EXECUTION` / `COMPLETED`.
     - Send back with human feedback → orchestrator merges with AI feedback and loops again.
     - Stop → `STOPPED`.
     - Fork → new task with inherited context and outputs.

### 15.4 Integration with Jobs and Background Runtime

- Background Runtime must understand review states:
  - It treats “review rounds” as **sub‑jobs** of the parent task.
  - Progress bar can combine:
    - % of planned steps completed.
    - % of required review rounds completed.

- For long tasks:
  - Runtime can pause between review rounds to respect rate limits or schedules.
  - Review rounds themselves can be run as background jobs to prevent blocking UI.
